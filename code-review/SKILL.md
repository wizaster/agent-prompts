When doing code review, we are expecting to provide constructive feedback that helps improve the quality of the code.
We should focus on specific code smells:
- **Afraid to fail**: The code is overly cautious, with excessive error handling or defensive programming that makes it hard to read or maintain. If it is expected that the code will fail, it should fail fast and clearly and the error thrown should be specific and actionnable (as much as possible). The code should not either create too many Error custom classes, or use generic Error classes that are not specific enough. The code should also not be too defensive, for example by checking for null values in places where it is not necessary.
- **Overly complex**: The code is difficult to understand due to its complexity. This can be due to deeply nested logic, long methods, or convoluted control flow. We should encourage simplification and refactoring to make the code more readable and maintainable.
-  **Code duplication**: The code contains repeated logic or patterns that could be abstracted into reusable functions or modules. We should encourage the use of DRY (Don't Repeat Yourself) principles to reduce duplication and improve maintainability. This also applies to duplicated code across different files or modules, not just within a single file (**BUT do not read the whole codebase to find duplicates, just check the file being reviewed**). This also aplies to duplicated code in tests, where we should encourage the use of test helpers or fixtures to reduce duplication. This also applies to alternative classes with different interfaces that implement the same logic, where we should encourage the use of a single interface and multiple implementations instead of duplicating logic across different classes.
- **Silent fallbacks**: The code should have clear and explicit happy paths for the deployed application. If some configurations must be handled differently because we are in a different environment (ex.: local vs production), we should make sure that the code is explicit about the differences and that it does not silently fallback to a default behavior that may not be appropriate for the current environment. We should encourage the use of configuration files or environment variables to handle different environments, and we should avoid hardcoding values or behaviors that may not be appropriate for all environments.
- **Shotgun surgery**: Introducing a change in one part of the codebase requires making changes in many other parts of the codebase. This can be a sign of poor separation of concerns or tight coupling between different modules. We should encourage refactoring to reduce coupling and improve modularity, making it easier to make changes without affecting other parts of the codebase.

In addition to these code smells, we should also be mindful of documentation maintenance. We want to ensure that the documentation is up to date and accurately reflects the current state of the codebase. This includes inline comments, README files, and any other relevant documentation. We should encourage developers to update documentation as part of their code changes, and we should also review documentation for clarity and completeness during code reviews.
